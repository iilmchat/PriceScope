# Правила разработки PriceScope

**Версия:** 1.0.3
**Обновлено:** 2026-11-24
**Назначение:** единый свод правил для команды и ассистента.

При работе над проектом **все** изменения должны соответствовать этим правилам.
Нарушение → комментарий в code review + ссылка на конкретный пункт.

---

## 1. Базовые правила

| # | Правило |
|---|---|
| 1.1 | Комментарии и docstring — **на русском языке**; имена идентификаторов — английские |
| 1.2 | Публичные классы/функции имеют docstring (`summary`, `Args`, `Returns`, `Raises`) |
| 1.3 | Зависимости — через конструктор/`Depends`, никаких глобальных `get_*()` вне DI |
| 1.4 | Все I/O-функции — `async def` с суффиксом `_async` (или `async_` префиксом); синхронный requests — только внутри адаптеров с явным комментарием |
| 1.5 | Public — `snake_case` (Python) / `lowerCamelCase` (Dart); приватные — `_leading_underscore` |
| 1.6 | API-контроллеры: единый формат ответа `{success, data, error, trace_id}`; исключения → middleware |
| 1.7 | Сервисы: `raise ... from exc`, не гасить стек; пользовательские ошибки — `DomainError` с кодом |
| 1.8 | `structlog` — технические логи; `AuditLog` — действия (импорт/экспорт/review) |
| 1.9 | Все пути — через `Path` + проверка на `..` (traversal); пользовательский ввод не попадает в путь напрямую |
| 1.10 | CLI-аргументы — `argparse`/`typer`, никакой конкатенации строк для команд |
| 1.11 | Версия — единственный источник `pyproject.toml` (`project.version`); дублирование в коде запрещено |
| 1.12 | Copyright в документации: `© 2026 PriceScope · v0.1.0` |
| 1.13 | Все проблемы → `docs/KNOWN_ISSUES.md` с номером `PL-XXX` |
| 1.14 | Новый REST-контракт = Pydantic-схема + тест контракта + версия в `schema_version` |
| 1.15 | Новый адаптер = 1 класс + 1 строка в `registry.py` + фикстуры + контрактный тест |

## 2. Документация (обновляется **в том же коммите** с кодом)

| # | Правило |
|---|---|
| 2.1 | `CHANGELOG.md` (Keep a Changelog) — обновляется вместе с кодом, не задним числом |
| 2.2 | Секция `[Unreleased]` — рабочая; при релизе → `[X.Y.Z] — YYYY-MM-DD`, сверху — пустая `[Unreleased]` |
| 2.3 | `README.md` — обновляется при изменении CLI/API/установки/требований |
| 2.4 | `docs/KNOWN_ISSUES.md` — любая найденная проблема (даже «не баг») → запись `PL-XXX` |
| 2.5 | `docs/development/vX.Y/DESIGN*.md` — дизайн-документ для крупных фаз |
| 2.6 | Секреты/credentials — **никогда** в git (только env / User Secrets / secret manager) |
| 2.7 | После релиза — обновить `pyproject.toml` (`version`) и `CHANGELOG.md` |
| 2.8 | Ссылки на PL в commit message — обязательны, если фикс связан с реестром |
| 2.9 | `docs/development/RELEASES.md` — единый чек-лист релиза |
| 2.10 | Markdown-файлы с внутренними code-блоками — выводить в 4 бэктиках снаружи (````). Иначе при копировании из чата внутренние блоки «съедаются» |
| 2.11 | Большие MD-файлы (README, RULES, ARCHITECTURE, RELEASES) — не выводить в чат целиком; только точечный diff или отдельная секция |
| 2.12 | Относительные ссылки в docs; проверка — `scripts/ci/check-doc-links.ps1` |
| 2.13 | Отчёт о фазе/задаче — по шаблону 7 разделов (RULES § 2.14), файл `docs/development/reports/vX.Y/<TASK>.md` |
| 2.14 | Шаблон отчёта: **(1)** Файлы (+/−) · **(2)** Покрытие (тесты) · **(3)** Результаты (pytest/ruff/mypy) · **(4)** Smoke (ручной сценарий) · **(5)** Что не так (риски) · **(6)** Новые PL · **(7)** Обоснование архитектуры |

Типы записей в CHANGELOG: `Added`, `Changed`, `Deprecated`, `Removed`, `Fixed`, `Security`.

## 3. Рабочий процесс (workflow)

| # | Правило |
|---|---|
| 3.1 | Маленькие шаги — крупная фича разбивается на 3-5 подшагов |
| 3.2 | 1 шаг = 1 коммит — не смешивать несвязанные изменения |
| 3.3 | `git add -A` вместо selective add |
| 3.4 | Перед коммитом — `git status --short` |
| 3.5 | После push — проверить GitHub Actions (CI зелёный) |
| 3.6 | Локально — `ruff check` + `mypy` **0 errors**, `pytest` зелёный |
| 3.7 | Тесты — все зелёные перед push |
| 3.8 | Fallback «работает локально, не в CI» — искать untracked/пропущенные файлы |
| 3.9 | Peer dependencies фиксируются в `pyproject.toml` с upper bound; обновление — отдельный коммит |
| 3.10 | Перед `alembic revision` — проверить `PRICESCOPE_MODE` / строку БД, чтобы не сгенерировать миграцию под не тот диалект |
| 3.11 | На новой машине — `git config user.email/name` до первого коммита |
| 3.12 | Перед push — `git log --all -p \| grep -i 'password\|secret\|token'` |
| 3.13 | Удаление мусора — после задач удалять временные скрипты (`fix-*.py`) |
| 3.14 | Перед импортом в БД — сделать backup `data/pricescope.db` (для local) |

## 4. Технические правила Python / FastAPI

| # | Правило | Причина |
|---|---|---|
| 4.1 | Деньги — **только `int` в минорных единицах**; конвертация `/100` — только на границе UI | float-ошибки в ценах |
| 4.2 | Все datetime — timezone-aware UTC; в SQLite хранить ISO-8601 с `Z` | KI-071-аналог: смещение при парсинге в JS |
| 4.3 | `Pydantic v2`: `model_config = ConfigDict(extra="forbid")` для входных DTO | лишние поля маскируют ошибки контракта |
| 4.4 | `BaseModel.model_dump(mode="json")` для `content_hash` — детерминированный JSON (`sort_keys=True`, `ensure_ascii=False`) | стабильность хэша |
| 4.5 | `asyncio.CancelledError` — не ловить broadly; только `finally` для очистки | внешняя отмена должна пробрасываться |
| 4.6 | Retry — только transient ошибки; таймаут через `asyncio.timeout()`, не через общий `client.timeout` changed late | analogRULES IIChatTools § 4.48 |
| 4.7 | `httpx.AsyncClient` — один на приложение (lifespan), не на запрос | пул соединений |
| 4.8 | SQLAlchemy: один `AsyncSession` на запрос (UoW), `commit()` в сервисе, не в репозитории | граница транзакции |
| 4.9 | Alembic-миграции не редактируются после применя в прод — только новая миграция | целостность истории |
| 4.10 | `content_hash` пересчитывается при любом изменении полей DTO; миграция = новая `schema_version` | идемпотентность |
| 4.11 | Списки в JSON-колонках хранятся компактно (`separators=(',', ':')`), без пробелов | воспроизводимый хэш |
| 4.12 | Логи — структурированные (`structlog`), без PII (телефоны/адреса клиентов) | приватность |
| 4.13 | Тесты не ходят в сеть: VCR/fixtures; live-тесты — с markers `@pytest.mark.live` и не в CI | стабильность CI |
| 4.14 | `pytest-asyncio` режим `auto`; name теста — `test_<что>_<условие>_<ожидание>` | читаемость отчётов |
| 4.15 | Изменение интерфейса (`Protocol`, `ABC`) → grep по всем реализациям и fake-заглушкам до запуска тестов | analog IIChatTools § 4.34 |
| 4.16 | Парсер не должен импортировать `pricescope_api` (только `core`) | разрыв слоёв |
| 4.17 | `trace_id` — `ContextVar`, проставляется middleware/CLI и пробрасывается в парсер | сквозная трассировка |
| 4.18 | Хардкод путей/координат/API-ключей — запрещён; только конфиг/env | переносимость |
| 4.19 | Flutter: бизнес-логика в `domain/usecases`, не в виджетах; UI не знает про Dio | чистая архитектура |
| 4.20 | Flutter: модели генерируются (`freezed`/`json_serializable`), ручной `fromJson` — только с комментарием | консистентность |
| 4.21 | Время и ожидание в инфраструктурных классах — инъецируемые (`clock`, `sleep`, `jitter`). Тесты не спят реальные секунды | детерминированные тесты retry/rate-limit (S02) |
| 4.22 | SQLite: `BigInteger` PK **не автоинкрементится**. Использовать `BigInteger().with_variant(Integer, "sqlite")`. После смены схемы удалить старый `data/*.db` и выполнить `init-db` | живой импорт падал с `NOT NULL constraint failed: observations.id` (PL-010) |
| 4.23 | `rowcount` у `ON CONFLICT DO UPDATE` одинаков для INSERT и UPDATE. Для счётчиков делать явный `SELECT` по уникальному ключу и различать `new/updated/unchanged` | PL-011 |
| 4.24 | Ошибку одной записи при массовом импорте изолировать `session.begin_nested()` (SAVEPOINT); внешнюю отмену — пробрасывать, но `ParseRun` завершать в `finally` | одна карточка не должна отравлять транзакцию |
| 4.25 | Все списковые REST-эндпоинты возвращают `data: {items, total, page, page_size, total_pages, has_next}`; `page_size ≤ 200`. Входные DTO — `extra="forbid"`, ошибки валидации — в едином envelope | контракт S04 |
| 4.26 | Схема БД изменяется **только** Alembic-миграцией; `pricescope init-db` = `upgrade head`, наследуемую БД без `alembic_version` — `stamp head`, не `create_all` | целостность истории цен |
| 4.27 | Браузерный доступ — только за портом (`BrowserBackend`), опциональные зависимости импортируются лениво. CAPTCHA → `CaptchaDetectedError` и останов; обход запрещён | ADR-006, тесты без Camoufox |

## 5. Безопасность и легальность парсинга

| # | Правило |
|---|---|
| 5.1 | Секреты — только env / `.env` (gitignored) / secret manager |
| 5.2 | `.env`, `*.db`, `data/`, `datasets/`, `logs/`, `LocalPackages/` — в `.gitignore` |
| 5.3 | Локальный API слушает **только** `127.0.0.1`; для LAN — явный флаг `--host` + предупреждение |
| 5.4 | Парсеры соблюдают robots.txt и ToS; частота запросов консервативная, UA честный |
| 5.5 | **CAPTCHA/антибот не обходится**: детект → останов + диагностика (ADR-006) |
| 5.6 | Утечка секрета — немедленная смена + `git filter-repo` только после смены |
| 5.7 | Перед push — `git log --all -p \| grep -i 'password\|secret\|token'` |
| 5.8 | GitHub Secret Scanning + Push Protection — включены (когда репо на GitHub) |

## 6. Git-специфичные правила

| # | Правило |
|---|---|
| 6.1 | `.gitignore` — обязателен для `bin/`, `__pycache__/`, `.venv/`, `*.db`, `data/`, `.env`, `logs/` |
| 6.2 | `.gitattributes` — `* text=auto eol=lf` |
| 6.3 | `.editorconfig` — UTF-8, 4 пробела (Python), 2 (Dart/YAML) |
| 6.4 | Формат commit: `<type>(<scope>): <subject>` + пустая строка + body |
| 6.5 | Типы: `feat`, `fix`, `docs`, `test`, `chore`, `refactor`, `security`, `perf` |
| 6.6 | Force-push — только `--force-with-lease` |
| 6.7 | `filter-repo` — только после смены скомпрометированных секретов |
| 6.8 | При merge — сначала `git fetch`, потом анализ конфликтов |
| 6.9 | `.gitkeep` — для пустых папок в репозитории |
